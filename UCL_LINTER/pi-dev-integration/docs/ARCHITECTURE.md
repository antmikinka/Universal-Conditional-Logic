# Architecture

The UCL-Tool x pi.dev integration is a two-stage pipeline that bridges
Python-based tool authoring with TypeScript-based prompt assembly.

---

## Module Responsibilities

### Python Side (tool authoring)

| Module | Responsibility |
|--------|---------------|
| `tool_domains.py` | Pre-built tool domains (FileSystem, Web, Playwright). Each domain encapsulates related tools with shared keywords. |
| `tool_export.py` | Serialization layer. Converts Python tool definitions to JSON matching the `UCLToolExport` schema. Provides `export_for_typescript()` and `migrate_prompt()`. |
| `builder.py` | Prompt construction. `UCLPromptBuilder` assembles UCL-formatted prompts directly in Python for server-side use. |
| `core.py` | UCL primitives. Defines `ToolDefinition`, `ToolParameter`, `ToolExample`, and the UCL encoding constants. |

### TypeScript Side (prompt assembly)

| Module | Responsibility |
|--------|---------------|
| `ucl-tool-types.ts` | Interface definitions. Mirrors the JSON export schema as TypeScript types for compile-time safety. |
| `ucl-tool-formatter.ts` | Formatting engine. Converts `UCLToolConfig` into UCL directive text or JSON Schema blocks. Contains `formatUCLToolsForPrompt()` and `replaceUCLPlaceholder()`. |
| `system-prompt-with-ucl.ts` | Integration point. Drop-in replacement for pi.dev's `buildSystemPrompt()` that adds `uclTools` and `enableUCLPlaceholders` options. |

### Bridge Artifact

| File | Purpose |
|------|---------|
| `ucl-tools-export.json` | The JSON contract between Python and TypeScript. Generated by `export_for_typescript()`, consumed by `import` in TypeScript. |

## Data Flow

### 1. Tool Definition (Python)

```python
class FileSystemDomain:
    def get_tools(self) -> List[ToolDefinition]:
        return [
            ToolDefinition(
                name="read_file",
                description="Read file content from disk",
                parameters=[
                    ToolParameter(name="path", type="string", required=True),
                    ToolParameter(name="encoding", type="string", required=False),
                ],
                keywords=["read", "file", "open", "load"],
            ),
            # ... more tools
        ]
```

### 2. Export (Python -> JSON)

```python
config = export_for_typescript(domains=["filesystem"])
# -> {
#   "version": "2.1",
#   "domains": [{
#     "name": "filesystem",
#     "tools": [{
#       "name": "read_file",
#       "parameters": [...],
#       "keywords": ["read", "file", "open", "load"]
#     }]
#   }],
#   "metadata": {"totalTools": 7, "overheadReduction": 78}
# }
```

### 3. Format (JSON -> UCL text)

```typescript
formatUCLToolsForPrompt(config)
// -> ^^CONDITION: {{concept:user_input}} CONTAINS "file" OR "read"...^^
//    <filesystem>
//        [[TOOL: read_file]]
//        [[DESC: Read file content from disk]]
//        [[PARAM: path, string, required]]
//        [[WHEN: read, file, open, load]]
//    </filesystem>
//    ^^/CONDITION^^
```

### 4. Inject (UCL text -> system prompt)

```typescript
buildSystemPrompt({
  cwd: process.cwd(),
  uclTools: config,
  enableUCLPlaceholders: true,
})
// -> Full system prompt with UCL tool block injected
```

## Design Decisions

### Why JSON as the bridge format?

JSON is the lowest-common-denominator between Python and TypeScript. Both
languages have native JSON support, and the schema is self-describing with
versioning. Alternative approaches considered:

- **Direct TypeScript generation**: Fragile; Python would need to know TS
  module structure.
- **gRPC/protobuf**: Overkill for a build-time artifact; adds runtime
  dependency.
- **Shared TypeScript types + ts-morph**: Requires TypeScript toolchain in
  Python environment.

### Why not generate UCL text in Python?

The TypeScript formatter is the integration point with pi.dev's prompt
assembly pipeline. Generating UCL in Python would bypass pi.dev's formatting
logic and make it harder to support features like `format: "json"` or
`format: "both"`.

### Why `groupTools` is optional

Grouping tools under shared conditions saves O_s but loses per-tool
activation granularity. Some use cases benefit from fine-grained activation
(e.g., a prompt that only needs `read_file` but not `delete_file`). The
default is `false` to preserve precision; set `true` for maximum compression.

## Extension Points

| Extension | How |
|-----------|-----|
| **New domain** | Subclass in `tool_domains.py`, register in the domain registry, re-export. |
| **Custom format** | Add a case in `formatUCLToolsForPrompt()` for a new `format` value. |
| **Runtime domain loading** | Replace `getBuiltinDomains()` with an async loader from the JSON file. |
| **Condition composition** | Extend `^^CONDITION^^` syntax to support AND/NOT operators. |
| **Token budgeting** | Add a `maxTokens` option that auto-selects domains based on character estimates. |
